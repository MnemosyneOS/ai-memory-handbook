# 构建篇

一个团队在两周内把记忆接进了产品：调通写入，接上检索，用户能感觉到「它记得我」。第四个月开始出问题——条目涨到八万条，召回开始返回三个月前的偏好；有人发现客服对话里贴过的一段 API key 被存了下来；产品经理要求删除某用户的全部记忆，工程答不出这会影响哪些功能。

三个问题分属写入、安全、删除，共同点是**功能跑通不等于机制建对**。构建篇处理的就是从「能跑」到「建对」之间的那段。

| 对应章节 | 维度 | 构建对象 | 主要机制 |
| --- | --- | --- | --- |
| 第 4 章 | 入口 | 什么内容以什么形态进入系统 | 单遍 ADD-only 抽取、双时间轴、五组分型、六类冲突与四操作 |
| 第 5 章 | 承载 | 数据存在哪里、如何隔离、如何压缩 | 物理隔离、SQLite 边界、热温冷分层、AIC 无损压缩 |
| 第 6 章 | 出口 | 什么内容在什么预算下进入上下文 | 五路信号融合、相关性下限、渐进式披露、预算感知 |
| 第 7 章 | 连接 | 外部系统如何调用这些能力 | MCP 工具面、REST 路由、框架适配、切换成本 |

四章构成一条数据通路：入口、承载、出口、连接。顺序不宜颠倒——先定入口形态，才能定存储结构；先定存储结构，才能定检索策略；三者定了，接入方式才有意义。

依赖关系上，第 4 章与第 5 章是硬依赖：写入的分型决定存储需要哪些字段与索引，存储的隔离方式又约束写入能携带的作用域。第 6 章依赖前两章，但可独立调优——检索参数不需要改存储。第 7 章最独立，它只关心接口形状，可以最后做。

只想解决一个问题时：召回不准从第 6 章进入，成本失控从第 5 章进入，接入困难从第 7 章进入。但读完四章会发现，多数表面问题都指向第 4 章——写入时没做结构化加工，后续任何环节都补不回来。
